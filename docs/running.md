# Running a job

[← Forja](../README.md)

Every piece of work in Forja is a job: a skill, a group check, a stage approval, a change, a migration. Jobs run in Forja's
engine; the desktop app starts them, shows them and answers their questions ([the desktop app](desktop-app.md)). While a job
writes a product, everything else can only read it.

## Products

| In the app | What it does |
|---|---|
| Home → New product | A new product: its name, its platforms (every product needs at least one); its areas open through gates, each stage approved before the next opens. Or an existing project: the path of its code; the platform is read from the code; every area is open, with no stage approvals, and the dashboard offers code-insight (it reverse-engineers the whole codebase: time and AI usage) or development straight away, neither recommended |
| Settings → Storage → Import | A product exported on another computer, or a backup: the full path of their `.forja` file or of a product folder (100 MB at most). Forja first shows what it holds, which generated files it will build again (pages, reports and generated documents are never taken from the file), every text written for an AI, and its repositories with an optional folder for each; nothing is added until you confirm; every item is checked against the model; the Forja versions must match exactly. There is no shared folder and no sync. Importing a product this computer has updates it: everything new or newer is taken, and an item changed here since refuses it. An export is one `<name>.forja` file: its record with every item's version, documents and reports, never your code, repository paths or the library cache |
| Deleting a product | The product's Settings → Delete…: Remove only (Forja forgets it: its entry in `_local/paths.json`, its job locks and its repository cache; the product folder stays) or Delete all (its folder and Forja's data for it are deleted too). Uninstalling never deletes products |
| Opening a product | Forja checks the version that wrote it: a product from an older Forja (0.7.3 on) is migrated first, no opt-out (the app shows the steps and their time). A product made before 0.7.3 is moved whole, untouched, into `<archive>/legacy/<date>/` on install, on update and by `forja migrate`. Every ticket and object is checked against the model: a file that breaks it is listed under Needs you, the product still opens, and skills skip that item until you fix it by hand. A question whose subject changed since it was asked says so under Needs you |

A repository you do not work on is never asked for: each repository's folder is asked only when a job needs it. the product's Settings → Repositories sets each repository's folder on this computer (or adds a repository); a repository with no folder here is listed under Needs you. A product whose folder moved is found again from Home (Locate folder…).

| Which repositories a job works on | How |
|---|---|
| Code insight and development | Every repository of the product is listed with its platform; tick one or more (explain-code and the report notes: one). The ones you ticked last time for that skill are ticked for you, never taken without you. A repository with no folder on this computer cannot be ticked until its folder is set. |
| A repository that is not listed | Other: choose its folder, then its platform: one Forja knows, or type what it is (java library, firmware, cli): that becomes its own platform (0.11.0). It is added to the product's repositories (the product's Settings → Repositories) when you answer, and a new empty Other box opens for the next one. A brand-new repository is created by hand first. |
| Several repositories ticked | One job over every repository: every repository's secrets check first, then every repository is planned and approved, one after another (each approval is final; a later repository's planner reads the plans approved before it). Only then is each repository written and built in turn. What the plans broke between the repositories (a compile error, a broken build, failing tests) is shown in the same job and planned as one fix across the repositories, which you approve once like a pull request; Forja writes it and checks every repository again. Each step also reads the other repositories (never changes them). A development ticket moves to Done with the last repository; code insight writes a report for each repository. |
| One order for every development skill | Repositories (1 or many) and their secrets checks → ticket → your documents → how the repository builds (its profile) → the skill's questions → a plan per repository (each approval final; every repository planned before any is written) → file operations → which tests run → write → build and checks → one fix across the repositories for what the plans broke → tests → report. Each skill only skips steps or adds its own: change-feature and refactor pin today's behaviour, write-tests checks its setup and asks about possible bugs, improve-coverage measures before and after, fix-bug finds the cause round by round, write-docs builds and tests nothing, review-code reviews one branch of one repository |
| How a repository builds | The first job on a repository has the project reader read what the repository is: its modules, build tool, the variant (Android flavours) or scheme (Xcode), the exact commands to compile and test, the kinds of tests and what each needs (a device, a simulator, Docker, a browser). Forja's scripts check it against the repository (folders, tools, `./gradlew tasks --all`, `xcodebuild -list`), you pick the variant or scheme when there are several, and you confirm it once (or say what is wrong). It is kept for the repository on this computer and read again only when a build file changes; every build and test run uses it |
| Your documents | Each file you give keeps its folder path in the run (`my-shop-docs/api/README.md`), so two files of one name never overwrite each other; a file whose content is already in the run is taken once ("already added"), and a path that doesn't exist is said. Your decision on a document with text written for an AI (keep or reject), and on one that can't be checked for secrets (read or skip), stands for the whole run: a bug's later rounds never ask again or drop it, and a document added in a later round is checked and asked about before the next agent reads it |
| Refactor | A target can be a method, a class, a file, a feature or a module, in any language. Targets (or a plan) that cover the whole repository, half the modules or more, or more than 50 files are a rebuild: the job stops before anything is planned or written, with **Pick a smaller part** or **Stop here** (use Modernize for the legacy codebase in Code insight) |
| Review code | One repository. You type **the branch to review** and **the branch it merges into**; a name that doesn't exist is asked again, listing the branches that do. The branch need not be checked out: its files are read from git, cleaned of secrets. Changes not committed yet are offered only when the branch to review is the one checked out |
| The architecture report reads everything (0.11.0) | Every file of the repository is read, with no line limit or budget, once: what each file holds is kept by its content, so a later run reads only the files that changed, were added or were removed. Generated code and build output are read only when you say so (it costs more tokens). Whether a kept report is still fresh is checked when a skill runs (every file's size, time and hash; new and deleted files too) and shown on the dashboard as the last run found it. A report is up to date when none of its files changed and Forja's rules for it are the same: it is reused. Out of date, you choose: Update it (only the changed files are read, and only the parts of the report they touch are rewritten; with no changed file, the report is rewritten under the new rules from what is known of each file, reading only the files Forja does not know yet) or Write it again (every file read from scratch). |
| What each repository is made of (0.11.1) | A script reads each repository's build files (Gradle, Maven, sbt, Xcode, Swift packages, CocoaPods, Carthage, Tuist, XcodeGen, Flutter, React Native, npm, yarn, pnpm, Nx, Turborepo, Lerna, Rush, Angular, Deno, Bun, Python, Go, Cargo, .NET, Composer, Bundler, CMake, Meson, Bazel, Buck2, Pants) without running them: each app or service is a component; a module used by one of them is inside it, one used by several is shared, one used by nothing is marked; tests and build logic are listed under the repository. The AI describes each of these and never adds, drops or moves one. One repository builds on another when its build names the other's coordinates; a vendored jar or AAR, or a near name, is a candidate the recorder confirms in the code |
| The design map (0.11.1) | One graph: each repository is a dashed frame in the lane of what it is (Clients, Services, Libraries), outside services in their own lane. A module used by one app sits inside it; one used by several sits on the frame's shared strip; one used by nothing is marked red; each box says how many use it. Every line is drawn; select a box to keep only its lines lit, and its details (where it is, what it uses, what uses it, what is inside it, other repositories and outside services it uses, its stories and decisions) show below the map, every name a link. A repository run alone while the others were not has its own tab, marked not linked yet, until the map is refreshed across every repository; otherwise there are no tabs. Items of two repositories are never merged |
| Architecture | A platform with one repository: its components and modules go there. Several, or none: each new component and module asks which repository it lives in (one), and Other can also plan a new repository with no code yet (its name and platform; set its folder in Settings once you create it). The stack and the start command are asked for every repository. |
| The start group | Its repositories and ticket are used by the next job of that skill only: the job empties the group. |

## What a job does

| Moment | What happens |
|---|---|
| A question | The question, one line on why it is asked, and its options. Nothing is assumed: a technical question has no default. A recommended option says why: `(Recommended: <reason>)`; technical questions name who to consult ("Not sure? Ask the mobile lead."). Every single choice has Other (type your own); an optional question has Skip |
| A Python project | The first job asks which Python runs the tests (usually the project's virtual environment) and keeps the answer for the repository on this computer only (every skill, fix-bug included, uses it; nobody is asked twice). Forja checks its version and the packages the project declares and stops with a message when they do not fit. It installs nothing. When no test command is found, the tech lead is asked for it once and it is kept for the repository, shared by the product |
| A story that does not work yet | It stays In Progress and lists why (a compile error, a failing test, tests that could not run or a test file that could not load); run it again (where the checks can run) to finish it. A ticket is Done only when the code compiles and the full unit-test suite passes; there is no Done anyway. A story's own problems are not raised as bug tickets |
| After every job | The skill's report and its kit's report are written (`reports/SKILL-<skill>.md`, `reports/KIT-<kit>.md`) and the product page is rebuilt (Overview, Design map, Requirements, Architecture, Plan, Tests, Questions, Changes, Documents and History; every id, run and status in it is a link, items not yet approved are marked) |
| After an architecture skill | Forja offers to build the updated design map now or continue with the next skill |
| An empty document | It is flagged at once and never read again: delete it from the product's documents, or keep it and add data before the next job |
| Something new or changed later | Run append-requirements, append-design or append-plan. It adds new items next to the old ones and never edits an old one. For each old item it replaces you say small (an edit, tried on a copy first, then you accept it) or major (the old item is discarded when nothing was built from it, else replaced; a ticket is closed `won't do` if not started, `cancelled` if in progress), and Forja lists the plans built from what was replaced so you can check them |
| A Jira ticket in a file | In an existing project a run can be for a Jira ticket saved as a file: Jira's XML export (recommended), its Word export (.doc), a PDF of the ticket, or a .txt / .md named after it. Every field the file holds becomes that field of the ticket: type, key, summary, description (a bug's Steps to reproduce / Expected / Actual when it has those headings), priority, status (moved only as the workflow allows: In Progress in Jira waits as To Do until the run starts it; Done keeps its resolution), component (when it names a repository of the product, else the run's repository), platform labels, story points, a spike's time box, parent or epic, issue links and sub-tasks (a key the product lacks becomes a placeholder), assignee, sprint and fix versions (shown in the ticket's field line). Acceptance criteria, other labels and components and attachment names go into the ticket's Notes. Comments and the reporter are never kept. Only what the file lacks is asked; everything read passes the gate, and an XML file that declares its own document type or entities is refused |
| Bugs | fix-bug lists the open bugs as `(id) Title` and lets you report one nobody has raised yet; no other skill offers bug tickets (fix the bug first), and fix-bug takes bugs only. A bug stays In Progress until the project works and its tests ran |
| Tests after a change | When production code changes, the whole test suite of its module runs, not only the new tests. A feature or change ends with unit tests for its ticket; you may decline them, and the reason is recorded with the job and shown in the report |
| Text written for an AI | Anything you type or paste, and every document, passes the gate first: secret-looking lines are removed, and invisible characters, hidden comments, hidden Word or web text, encoded blobs, role markers or phrases that tell an AI what to do stop it. Each place is shown; rejecting all of it is recommended |
| Your own words (Other) | The answer interpreter checks what you typed against every answer so far, the product's tickets and objects and its documents. It shows how it read your words and how serious a conflict is; for a conflict it lists what your answer would break (for example online only earlier, offline editing now) and asks one follow-up when something is missing. Keep its reading, answer the follow-up, change your words, or keep your exact words anyway with a reason (kept with the answer) |
| Recommend an answer | At a technical question, the recommender suggests one to three choices for this product, each with why it fits and its trade-off. It never answers for you. Not offered in requirements |
| What the requirements say | At a question that must meet requirements, the requirement expander says what those objects mean for this question: what they ask, which options meet them as they are, which need more work, and what they leave open. It never answers for you |
| Explaining a question | Every question has its explanation: what it asks, why it matters, what each choice leads to, and every Forja word in it (from the glossary) |
| Saved and found answers | Always first, always the same words: `Keep: <value>` and `Use what was found in <where>: <value>` |
| Question groups | An area's questions come in groups, one group on one page. An optional group you leave empty is skipped when you move on (or with Skip this group) and its questions are never asked again; a required question must be answered. Once every group of a skill is folded or skipped, the skill's job starts and writes the items from your answers. A stage's first review and approval open only after every skill before its review finished |
| One answer per question | Each question keeps one answer: a new choice replaces the earlier one. A must question cannot be skipped and offers no "Not decided yet"; a skipped optional question stores nothing |
| Changing an earlier answer | On the job's page, back to any earlier answer of the job. Forja first shows what it costs: the AI steps that run again, the items redone, the answers after it and the steps that changed code. What the job wrote in the product after that answer is undone; code a step already changed stays in the repository (Forja never reverts with git), and once your new answer is in, the job's agents rework that code from where it is to fit it, taking out what no longer fits; the answers after it are offered again, lists too, and once the changed answer is in they are checked against it: one it makes wrong is asked again with the reason |
| A skill's job that failed | Nothing it wrote is undone yet, and it stays that way after Forja closes. Its page offers **Retry from "<the step that failed>"**: the steps before it are given back as they were (no AI call again, the same answers) and the failed steps run again, then the rest. **Discard** undoes what it wrote, as for any job that did not finish. A job you stop yourself is undone at once, as before |
| The plan's review | Every code skill's plan (a feature or change, refactor, tests, coverage, a bug fix, documentation) is low level: the full code of every file, a change to a file that exists as its exact lines, a new file as its whole text. It is shown in its Approve question, in the job screen, like a pull request (every file expands and collapses, line numbers, green additions and red removals), with the requirements from the ticket each test covers. A plan with a file it gives no code for goes back to the planner. When the job ends, what it really changed is shown the same way |
| What Forja writes | The code you approved, exactly as previewed: Forja places each change by the lines around it and carries every earlier change's shift (a line added at 10 moves the change meant for 50 to 51). Only a change whose lines are no longer in the file (it changed since the plan) goes to its writer, and those files are shown to you before the job goes on (keep them, or stop and Discard) |
| File operations | After you approve, every new file, copy, move and delete of the plan is listed, one row each with its full path, ticked: Forja does the ticked ones itself. A path's missing folders are said once (`copy logo.png → app/src/main/res/drawable-xxhdpi/logo.png (creates drawable-xxhdpi/)`) and created. A copied or moved file keeps its own name unless the plan says why, and a resource the code uses (`R.drawable.logo`, `@drawable/logo`) must exist under that name. Discard undoes all of them |
| The versions a project runs on | Before planning, every code skill reads (no AI) the project's runtime and language versions, what already sets library versions (a parent POM, a BOM, a version catalog, a lock file) and the libraries it has, for every stack Forja knows: `WORKSPACE/VERSIONS.json`. A test setup that adds a library must give its exact version, or none when a parent or BOM sets it; a library of a family the project already has takes that family's version; a new one must run on the project's runtime (the kit's table: Mockito 5 needs Java 11, JUnit 6 Java 17, Jest 30 Node 18, PHPUnit 10 PHP 8.1 …). A plan that breaks these goes back to the planner before you approve it |
| Which tests run | Asked once after the plan's approval, for every code skill: the full test suite (recommended), only the new and changed tests, build only (no test runs; the code must compile), or the commands for you to run (the job waits for your results). A typed answer is read for what it says ("don't run the tests" is build only); one that says none of these is asked again, never guessed. The choice covers every run of the job: the check before anything is written, the tests that pin today's behaviour (written but not run without tests), a bug fix's checks and the end. Build only and new compile only the modules the work touches and the ones that depend on them. Then the project's state before anything is written: it builds, its dependencies resolve, which tests already fail |
| Tests that need more than this computer | Write tests and improve coverage ask, only when you chose such kinds, which of them Forja runs here (a device or emulator, a simulator, Docker, a browser: as the repository's profile says); the unticked ones are your commands. "Which tests run" after approval names what you chose here |
| While it runs | A build or a test run shows, under its step, what runs (the command, the module, n of m), how long it has run and the last lines of its output |
| The test setup is checked | Right after the setup (libraries, a test configuration) is written, the project is checked as before it: the stack's own dependency check (`npm ls`, `pip check`, `dotnet restore`, `go mod verify`, `bundle check`, `cargo metadata` …), the build and, with the full suite, every test. What it broke goes back to the setup writer once; still broken, the job fails there, kept for Retry or Discard, before any test is written on it |
| When a job is done | A feature, a change, a refactor, a bug fix, tests or coverage is done only when the project builds and the tests you chose pass. Tests that already failed before the run are listed in the report, never blamed on it. The ticket moves to Done only then |
| The build doctor (0.11.0) | When the compile, the build or the tests fail after a job wrote its code, the build doctor (a strong-model agent) reads the logs and the code and shows you what failed, why (with the file and line), whether it was already broken before the job, and the one fix it recommends (other ways in a line each). **Apply the recommended fix**: Forja writes it (kept for Discard) and builds again; a new failure gets a new finding. **Other**: type what you want instead ("the test is wrong, not the code"); the doctor reads your words and proposes again. **Stop here**: the code stays as written, the job ends failed; fix it in your editor, then Retry runs the checks again, or Discard undoes the job. It goes on until the build passes or you stop. Failing new tests get the test writer's own round first (a wrong test, or a possible bug for you to decide) |
| Forja-Agent (0.11.0) | One agent sits in the middle of every job: every kit's skills and Forja's own jobs (resolving a clash, changing an item, a spike), following its kit's playbook. It reads everything the product has after the gates (your documents as cleaned copies, every answer you gave, the product's items, the cleaned code of repositories already checked for secrets), works out what they mean even when no document says it word for word, asks you what only you can decide, proposes its reading of the job, and prefills the job's questions: each one shows its answer first, with its evidence and why ("Proposed by Forja-Agent"), and you confirm, edit or pick another; one the gate held shows what it found, and words where a choice is needed are read into the choice they mean (else shown beside the question). Every answer can be changed later. It keeps notes on what it read, by each file's content: a later job reads the notes, and only new or changed files again. When its AI call can't run (offline), the job says so and asks its questions as usual. A usage limit pauses Forja: the job waits for Resume, every other job waits at its next AI step and nothing new starts, until the limit resets or another AI tool is active (Settings → AI tools). Write tests: after your documents and the repository's profile, it reads the ticket, the documents, your answers and the code, runs Forja's tools for what it can't read (the libraries and versions from the build tool itself, the code generators, generating their code, compiling), asks you only what it can't settle (options from this repository, one recommended with why, Other always), proposes its test strategy for you to confirm or change, and hands it to the planner. Each turn is one AI call over the job's notebook (kept in the run's record with the strategy); a job may take up to 100 turns (Settings → AI tools). Generated code (OpenAPI, protobuf …) is never tested itself: the code that implements or uses it is. The other development skills: it reads the kit's own questions first and answers what the ticket, the documents, your answers and the code settle; the kit asks only the rest. New feature finds the feature to build like and the designs the ticket names; change feature finds the feature's files with why; refactor says why a large target is still a refactor; improve coverage proposes where coverage matters; write docs proposes where the documents go (into the codebase, in your next commit, or kept in Forja only) and what each explains; review code checks the branch against the ticket it is for (always asked) as well as the checklist |
| Imports and libraries (0.11.0) | Before you see a plan, every file of it is checked against the libraries the build really has, in the right scope: a JUnit 4 import in a JUnit 5 project, a library the project doesn't have and the plan doesn't add, a change inside generated code, or a pom change that moves a library main code uses to the test scope goes back to the planner with the exact lines. Maven and Gradle are asked for their libraries (parents and BOMs included); a module that inherits JUnit or `spring-boot-starter-test` is never told it is missing |
| Other on every question (0.11.0) | Every choice question has Other: type what you want. A step that needs one of the choices has your words read into the one they mean (shown back: Read as …), or asked again when none fits |
| A test that finds a bug | In write-tests and improve-coverage (which never change production code), a new test that fails because the code does not do what the requirement says is shown to you: the test, the requirement it checks, what happened and why it looks like a bug. **Yes** raises a bug ticket and skips that test with the bug's id, so the job can finish; **No** (with what the test got wrong) sends your words to the test writer once |
| The same ticket twice | A ticket file or paste with a key or title the product has is compared with it: the same (type, title and text) is that ticket, never a second one; small changes make a new version of it (its history keeps the old one); other content is a new ticket beside it |
| Leaving a job | A job that asks waits for you under Being worked (the dashboard and the title bar), even after the app is closed and opened again. Stop ends it and undoes what it half wrote |
| A usage limit | Forja pauses (0.11.0): the job waits on Resume, every other job waits at its next AI step, and nothing new starts (Retry included); the title bar says Paused. Wait for the limit to reset, or make another AI tool active in Settings → AI tools, then Resume runs the same step on the tool active then. Stop still ends the job, kept for Retry |
| A plan that can't be applied | Forja shows every reason (a file with secrets, a file that doesn't exist, a module or build file that isn't this repository's) and sends the plan back to the planner once. If it's still wrong, you choose what happens; it never repeats on its own |
| The end | The job's tickets and objects in the product, its line in the job log (`forja jobs` in the terminal), its record and outputs in `runs/<id>/`, and `FORJA-USAGE.md` with time, tokens and cost per agent. Copilot does not report tokens. The skill that usually comes next is offered |

## The product report

The product's Reports write the status as Markdown, at three levels, with no AI, into `generated-documents/reports/`:
`PRODUCT-REPORT.md` (Overview, What needs attention, Technical details: every kit in lifecycle order), `KIT-<kit>.md` (its skills,
what comes next, what it wrote) and `SKILL-<skill>.md` (every job of it). Each job shows its state, every question it asked with the
answer given (`<id>#<n>`) and the role that answered, and what it wrote with what that is now. A product migrated from an earlier
Forja keeps its old skill reports inside the area reports (`AREA-<area>.md`).

| A kit that... | Its section shows |
|---|---|
| never ran on the product | "<kit> wasn't run for this product." |
| ran | its jobs (when, skill, state, questions and answers, what each wrote and what it is now) |

What needs attention lists open findings, open and in-review questions and outdated work.

## Jira

Tickets mirror Jira's issue types (feature, epic, story, task, sub-task, bug, spike), fields, links and workflow one to one, so a
future connection maps them directly. A ticket's component is the repository that builds it; its labels are its platforms (or qa,
foundation, change); a change ticket links `replaces` to the ticket it replaces; `blocked_by` links say what waits for what. There is no CSV export.

## How many agents at once

3 by default, which keeps you clear of subscription rate limits and keeps a job's cost easy to follow. Raise it in Settings → Tools
(Agents at once) on an API key or a higher plan.

## Steps that happen outside Forja

| Step | Why it stays outside |
|---|---|
| Offline review (`offline-review-<n>`): the points one fix round could not settle, most severe first; each point's answer is entered in the app's Offline reviews | People settle what Forja cannot |
| Committing the changes a development job made | Forja never handles git |
| fix-bug temporary logs: you reproduce the bug on your device; Forja waits | Only you can drive the app |
| Device or interface checks a plan lists as manual | They need a device |
| Signing in to an AI tool: `claude`, `codex login` or `copilot` | Once, in the tool itself |

How the stages fit together, approvals and changes to approved work: [the lifecycle](lifecycle.md).

## The document library

A new job starts by offering the product's documents: a folder or files (requirements, briefs, designs and screenshots,
diagrams, notes, exports in md, txt, pdf, docx, xlsx, pptx, json, html, csv, or pictures). 0.11.0: they are cleaned the moment
they are taken (converted, secret-looking lines removed, the prompt gate) and only the cleaned copies are kept
(`<product>/library/docs/`); the copies as given are deleted. Pictures are read as they are. A document holding text written
for an AI (secrets removed) and any other file that can't be checked for secrets (a scanned PDF, a file that isn't text) wait on
this computer, outside the product and out of every agent's reach, never exported; each job asks about them for that job only
(the next job asks again, so you can change your mind). They are read once by the
document reader, which keeps what they say with quotes and places in `<product>/library/library.json`. The product keeps the
choice (use it, add more, read again, or none); only new or changed files are read again. 0.11.0: the product's documents feed
the requirements, architecture, planning and test jobs only; each is read in full once, in the job where it arrives, and later
jobs get what was found in them, Forja-Agent's notes and the items, never every document again. Development and code insight
jobs never read them. Discarding a job takes back out the documents it brought in.

When a document answers a question, the question shows it first, with its quote and file: confirm it, edit it (your edit goes to
the answer interpreter), or pick another answer. Nothing is taken silently. Each job keeps `DOCUMENT-FINDINGS.md` in its
`outputs/`: every answer the documents gave and what you did with it. Pictures are read by AI tools that open images (Claude Code);
others list them as not read. Every answer you give is kept in the job that asked it (`runs/<id>/run.json`), or as a draft answer
of its question group until a job takes it.
